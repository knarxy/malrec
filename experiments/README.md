# Experiments

Each of these answers one question with a measurement, and the answer is why
the production code looks the way it does. They run against the live dev
database and print a table; none of them are imported by the package.

```bash
set -a && . ../.env && set +a
../.venv/bin/python exp_implicit.py
```

## The benchmark: `make bench`

`bench.py` is the gate for every ranking change. It runs on the server
against a frozen snapshot (public lists, catalogue, the reference profile -
`make bench-snapshot`, kept under `bench/data/`, never in git) and the
production code: `fit_user`, `HybridScorer`, `rank.score_candidates`,
`rank.rerank`, for 300 held-out users at 25 / 150 / 400 list entries and the
reference profile's 8 splits. The tabs are built as served: the long-memory
model when `safe_bets_memory_mix` is on, and each enabled tab's learned order
(trained on the snapshot, cached by a hash of its code and settings). Each
metric (rho, RMSE; recall@50, IPS-weighted recall@50, hit@10, bad@10 of Safe
Bets; recall@50, IPS recall@50 and hit@10 of Discover and Hidden Gems) is
compared per user with `bench/baseline.json`; anything worse by more than
two standard errors fails the run, and settings that differ from the
baseline's are named. About 8 minutes with cached models; the population
model is refitted (≈6 minutes) only when its code changes, a learned order
(≈25-35 minutes per tab) when its code or settings do. Two runs on the same
code agree to the last digit. `make bench-baseline` records a new baseline
once a change is accepted.

`exp_blend.py` runs the benchmark once per arm, each arm a set of setting
overrides (`all:discover_ranker_weight=0.5:0.5`), and prints every metric
paired with the first arm; `results_points_2026-10-11.txt` is the run that
decided the long-memory mix, the key's risk share, the popularity-corrected
labels and the Discover / Hidden Gems rankers (docs/RESEARCH.md).

## Protocol

Protocol throughout: temporal holdout at 8 sizes (25…60), reporting mean
Spearman / nDCG@10 / RMSE **and the per-split win count**, so a lucky average
is visible as such. Random K-fold is never used — it lets the model train on
2026 ratings to predict a 2018 one.

| script | question | verdict |
|---|---|---|
| `exp_implicit.py` | Does the unscored half of a list carry signal? | **kept** — ρ 0.756 → 0.769, nDCG 0.797 → 0.810, 7/8 splits |
| `exp_rank.py` | Is a ranking objective better than score regression? | **rejected** — pairwise ρ 0.730, LambdaMART 0.547, vs ridge 0.778; lost every split |
| `exp_embed.py` | Do synopsis embeddings add anything over AniList tags? | **rejected** — kNN feature ±0.003, SVD columns −0.05 to −0.15 |
| `exp_notforme.py` | What should "Not for me" do beyond hiding the title? | **shipped** — implicit rating −1 under the mean at weight 0.4 (personal model and population fold-in) plus hiding the franchise: hit@10 +0.024 at 150 entries, recall@50 +0.008 at 400, ρ cost within noise; −2/0.8 and stronger cost ρ 0.03–0.04 |
| `exp_twotower.py` | Does a two-tower model (PyTorch) beat the shipped relevance signal? | **not shipped** — as relevance: neutral at 150/400 entries, worse for the reference profile (recall@50 −0.025); at 25 entries +0.017 recall@50 / +0.054 hit@10 but the lists turn mainstream (median popularity #113 → #59) and less personal (overlap 0.06 → 0.13). Titles nobody in training listed: production never ranks one into the top 50 (0 %), the two-tower alone finds 13–14 % of the liked ones, the mix loses that again |

`exp_embed.py` needs `pip install model2vec`, which is deliberately not a
project dependency since the result was negative.

## Notes on the negative results

**Two-tower retrieval is set aside, not disproven (2026-10-09).** Results in
`results_twotower_2026-10-09.txt`. As a replacement for, or a half share of,
the relevance signal it is at best neutral beyond thin lists and costs the
reference profile recall; on 25-entry lists its gain comes with mainstream,
less personal lists - the problem relevance was introduced to fix. What it
does that nothing in production does: place a title no training list
contains (13-14 % recall@50 on such titles, production 0 %). Mixed into the
order key that advantage disappears, so it would need a place of its own -
ordering This Season / Coming Soon, or a slot for titles without list data -
and that is worth testing only once the usage log (`app_event`) shows how
those tabs are used. To rerun: torch goes into `/work/.torchlib` on the
server (`pip install --target /work/.torchlib torch --index-url
https://download.pytorch.org/whl/cpu`, CPU wheel ~0.9 GB installed, never in
the API image), then `PYTHONPATH=/work/src:/work:/work/.torchlib python -m
experiments.exp_twotower`.

**Ranking objectives lose because of sample size, not principle.** A pairwise
model has to learn from ~10k pairs generated by ~180 rows; the pairs are not
independent, so the effective sample is still ~180 while the variance is much
higher. Ridge's shrinkage is worth more here than optimising the right loss.
The trend was monotonic — the more regularised the pairwise model, the closer
it got to ridge without ever passing it. Worth revisiting at a few thousand
ratings, not before.

**Embeddings lose because tags already won.** AniList's ~22 weighted tags per
anime are human-curated and describe premise directly ("Time Manipulation",
"Death Game", "Primarily Adult Cast"). A synopsis embedding is a noisier route
to the same information, and 48 extra dense columns on ~180 training rows cost
far more in variance than they return.
